# Phase two: namespace ordering, shared limits and pinned outbound requests

This change follows the first repair batch. It is not a claim that all production
or real-device scenarios have been verified. The installation, activation,
application deployment and production checks are separate gates.

## Data API compatibility

The four account data endpoints (`playrecords`, `favorites`, `searchhistory`,
`followings`) retain their GET JSON shapes. Successful GET responses carry
`X-MoonTV-Epoch` and `X-MoonTV-Revision` from the same locked database snapshot
as their data. Responses are private and not cacheable. A single-item GET carries
the namespace revision while still applying the existing source/adult filters.

Every POST/DELETE requires those two preconditions plus a UUID
`X-MoonTV-Operation-Id`. Missing headers return 428 (refresh/upgrade), malformed
headers return 400, concurrent changes return 409, and unavailable protocol/RPCs
return 503. There is no fallback to unconditional KV writes. A clear is one
versioned transaction rather than independently deleting a list of keys.

Record/favorite/following writes must include a finite `save_time` in the original
payload. The server does not invent a different timestamp on each retry, which
would change the content bound to an operation ID. Third-party clients must
upgrade; version headers must come from the data snapshot the user actually saw,
not a new version fetched solely to force a stale write through.

A successful response advances the namespace revision. A retry must use the exact
original operation ID, payload and expected version. Only the latest receipt per
namespace is retained. If another writer has advanced the namespace, an old
request may conflict even if it previously succeeded. A conflict after a lost
response must not be represented as proof that the original request rolled back.
The browser preserves local intent and requires explicit recovery/reconfirmation
instead of automatically merging timestamps or replaying stale progress.

## Database gates and lifecycle

The namespace migration installs a dormant write guard and server-only metadata.
Activation is a separate reviewed operation. A dormant install does not provide
ordering guarantees, and the new versioned RPCs fail closed while dormant.
Once activated, old application/preview workers cannot bypass the protocol by
writing the managed KV namespaces directly. They fail rather than overwrite new
state. Ordinary mutations use compatible table write-intent locks and a per-user
transaction advisory lock. Full restore retains its broad replacement lock.

Account deletion/re-registration and full restore invalidate old namespace epochs;
old devices cannot write through a deleted and recreated account identity. The
maintenance refresh paths use versions tied to their original read objects and do
not fetch a new precondition for an old object. Unversioned legacy storage setters
are not a supported bypass.

Installing a restore/delete function is not permission to execute it on production
user data. No real account or backup restore should be used merely as a smoke test.
Recovery availability must be verified separately before destructive operations.

See [the namespace migration runbook](../../migrations/supabase/NAMESPACE_PROTOCOL.md) for exact ACLs, activation, lock order,
rollback and local SQL tests. See [shared limits](2026-10-26-shared-rate-limits.md)
and [pinned transport](2026-10-26-pinned-transport.md) for their specific contracts.

## Release gates

1. Review migrations and their service-only privileges independently. Do not
   execute them automatically from application startup.
2. Verify the old/new application overlap, dormant-install and activation order.
   The cutover can temporarily reject managed data requests. Obtain approval for
   that impact before applying activation or changing access controls.
3. Run final full tests, strict lint, typecheck and production build on the exact
   tree; run SQL regressions and socket/TLS harnesses separately.
4. Confirm the deployed Node version supports the runtime transport dependency.
   Docker and hosted runtime must use Node 22.19 or later in the 22.x line.
5. Verify Preview with authenticated image/playlist requests, redirects and Range;
   a login page or anonymous 401 does not exercise outbound transport.
6. Publish/merge only within the user's release authorization, verify exact remote
   commit and CI, then confirm production deployment and non-destructive health.

## Limits

Local SQL tests use PGlite and deterministic interleavings. They do not establish
real multi-connection PostgreSQL lock contention or hosted PostgREST behavior.
Local sockets exercise the actual pinned connector and TLS checks but do not
establish hosted routing/egress compatibility. No real-device video decode,
full production backup/restore drill, production user-data write test or load test
is implied by unit tests. Shared rate limits add database round trips and writes;
they are not a network-level DDoS protection service.
